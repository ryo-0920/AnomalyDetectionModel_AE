# trace-spec-to-code

レビュー、検証、リリース準備の際に、要求、テストケース定義、実行可能受け入れテスト、実装変更がつながっていることを確認するために使う。

## 目的
承認済み仕様からテストケース定義、実行可能受け入れテスト、実装ファイルまでの軽量な追跡を作る。

## 入力
- 有効な `docs/specs/**` ファイル。
- `.codex/test-cases/**` にあるテストケース定義。
- 変更された実装ファイル。
- 変更されたテストファイル。
- README または公開インターフェイス文書。
- 検証結果。

## sub-agent 運用
- メインエージェントは、レビュー、検証、リリース準備で追跡確認が必要な場合、`validator` を sub-agent として必ず起動する。
- sub-agent の `reasoning_effort` は、`AGENTS.md` のエージェント協働に定義された方針に従う。
- 編集を伴う validator は、実行環境が対応する場合 `worker` として起動し、担当成果物、`write_scope`、他者変更を戻さないことを明示する。
- `validator` は必要な `.codex/traceability/**` またはレビューメモを直接作成または更新する。メインエージェントは、利用可能な `validator` の追跡成果物を代行編集しない。
- 同一追跡確認内の差し戻しでは、既に起動した sub-agent を再利用し、再確認のたびに新しい sub-agent を spawn しない。
- `validator` は要求、テストケース定義、実行可能受け入れテスト、実装、検証結果の対応を確認する。
- 仕様意図や受け入れ条件の解釈が不明な場合は、必要に応じて `spec-designer` または `test-designer` へ差し戻す。
- 必要な sub-agent を起動できない場合、またはユーザー依頼に sub-agent 利用の明示がなく実行環境の上位ルールにより起動できない場合、追跡確認を開始しない。
- 起動できない場合は、理由と次の依頼文をユーザーへ返して停止する: `multi-agent 標準運用で進めてください。追跡確認では validator を使ってください。`

## 手順
1. 関連する要求と受け入れ条件を列挙する。
2. 各項目をテストケース定義に対応付ける。
3. 各項目を実行可能受け入れテスト、または文書化された手動チェックに対応付ける。
4. 各項目を実装ファイルに対応付ける。
5. テストケース定義はあるが実行可能テストまたは手動チェックがない要求を特定する。
6. 実装はあるが検証がない要求を特定する。
7. 現行要求に対応しなくなったテストを特定する。
8. 有用な場合は、`.codex/traceability/<feature>.yaml` または短いレビューメモに記録する。
9. `.codex/traceability/` が存在しない場合は、成果物を書き込む時点で親ディレクトリを作成する。
10. sub-agent が直接編集した追跡ファイルを確認する。メインエージェントによる直接編集は、機械的統合、衝突解消、標準導入や標準更新そのもの、またはユーザーが明示した例外に限る。

## 出力
- 要求、テストケース定義、実行可能受け入れテスト、コードの対応。
- sub-agent が直接編集した追跡ファイル。
- 不足または弱い検証箇所。
- 文書更新の必要性。
- PR 準備可否または統合可否に関する懸念。
- 使用した sub-agent。

## ガードレール
- 追跡は軽量に保ち、対象変更に近い範囲に絞る。
- 必須 sub-agent が未使用の場合、このワークフローを完了扱いにしない。
- リポジトリが要求しない限り、小さな変更に重いプロセス成果物を作らない。
- 実際の検証が存在しない限り、要求がテストで対応済みだと扱わない。
